# 从“提交资料”到“审核闭环”：我如何用原生 JavaScript 做一个商品上架审核工具

## 项目背景

电商运营上架商品时，经常需要同时处理商品名称、价格、库存、供应商、图片和详情说明。资料收集完成后，还要交给审核人员检查。如果资料散落在聊天记录和表格里，容易出现版本混乱、驳回原因丢失、修改后重复出错等问题。

因此，我以“商品上架与资料审核”为选题，设计并实现了「商审台」。项目目标不是简单做一个商品列表，而是把资料填写、提交、审核、驳回、修改、重提和最终通过组织成一条可追踪的流程。

## 需求拆解

项目包含两个主要角色：

1. 运营人员：创建和编辑商品资料，完成必填项检查后提交审核。
2. 审核人员：查看商品详情和历史记录，给出通过或驳回结论。

审核规则如下：

- 草稿可以编辑和提交。
- 待审核资料暂时锁定，避免审核过程中内容发生变化。
- 审核驳回必须填写原因。
- 被驳回的商品修改后可以重新提交。
- 审核通过后锁定商品资料。
- 每一次创建、修改、提交、通过和驳回都会写入时间线。

## 技术方案

项目使用原生 HTML、CSS 和 JavaScript，不依赖前端框架或构建工具，达到“打开即可运行”和“直接部署静态页面”的目标。

### 1. 业务状态与界面分离

`state.js` 只负责业务规则，包括：

- 商品创建与更新；
- 完整性校验；
- 状态流转；
- 审核原因；
- 审计记录；
- 统计汇总。

`app.js` 负责界面渲染、事件绑定和 `localStorage` 持久化。这样审核规则可以通过 Node.js 独立测试，不依赖浏览器。

### 2. 明确的状态机

商品的四个状态为：

- `draft`：草稿；
- `pending`：待审核；
- `approved`：已通过；
- `rejected`：已驳回。

合法流转关系集中在 `TRANSITIONS` 中，避免界面按钮遗漏规则。例如，待审核商品不能被编辑，已通过商品不能被修改或重复流转。

### 3. 完整性检查和审核解耦

系统提交前会检查商品名称、编码、分类、价格、库存、供应商和详情说明。审核人员看到的是已经满足最低提交条件的资料，但依然可以因为业务质量不合格而驳回。

### 4. 本地持久化

演示版使用浏览器 `localStorage` 保存数据，并限制上传图片大小。这样做不依赖服务端，也适合作为 GitHub Pages 上的公开演示。

### 5. 可访问和响应式界面

页面通过语义化标签、键盘可操作按钮、可见焦点状态和 `aria-live` 提示提升可用性。布局同时适配桌面与手机。

## 自动测试

项目使用 Node.js 内置测试运行器，覆盖：

- 商品草稿创建；
- 必填资料校验；
- 提交、驳回、修正、重提、通过；
- 不同状态数量与库存统计。

运行命令：

```bash
node --test tests/state.test.mjs
```

## 项目收获

这个项目让我意识到，业务工具的核心不只是“把字段做出来”，更重要的是把角色、状态、权限和异常路径设计清楚。尤其是“待审核时锁定”“驳回必须填写原因”“每次操作可追溯”这些规则，决定了工具是否真正能够用于协作。
