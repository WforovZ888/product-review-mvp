BACKGROUND

为什么需要审核流程

商品上架涉及名称、价格、库存、供应商、图片和详情说明。资料散落在聊天与表格中时，容易出现版本混乱、驳回原因丢失和修改后重复出错等问题。

因此，我把项目从一个商品列表扩展为完整协作流程：运营创建资料、提交审核，审核人员查看详情并给出结论，驳回后修改重提，所有操作写入审计时间线。

STATE MACHINE

用状态机约束协作

草稿提交 →待审核通过 →已通过驳回 →已驳回修改后重提 ↺

待审核商品锁定，避免审核对象中途变化；驳回必须填写原因；审核通过后资料锁定，保证展示内容与审核结论一致。

ARCHITECTURE

业务规则与界面分离

state.js

创建、校验、状态流转、驳回原因、审计记录和统计。

app.js

页面渲染、事件绑定、图片预览与 localStorage 持久化。

Node Test

独立测试提交、驳回、修改重提、通过和统计规则。

QUALITY

完整性与留痕

系统检查名称、编码、分类、价格、库存、供应商和详情说明。提交前不满足最低条件会被阻止，审核人员仍可根据业务质量驳回。

4 项自动测试全部通过
node --test tests/state.test.mjs

界面支持搜索筛选、资料完整度、响应式布局、键盘焦点和审核时间线，让工具真正对应业务约束。

DELIVERY

从项目到公网演示

项目采用无构建依赖的静态架构，直接部署到 GitHub Pages。演示数据只保存在当前浏览器，不包含真实商品或个人信息。

项目收获

一个业务工具的核心不只是把字段做出来，而是把角色、状态、权限和异常路径设计清楚。“待审核时锁定”“驳回必须填写原因”“每次操作可追溯”这些规则，决定了它是否能真正用于协作。
